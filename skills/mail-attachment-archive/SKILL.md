# 阶段性邮件附件整理归档

目标是先保留有价值的附件，再让用户决定如何处理独立副本和历史邮件。执行前读取[共用工具契约](../references/arkive-tools.md)，按其中的格式分流、备份、归档和结果判断规则执行。

## 取得阶段范围与本地附件

明确用户说的阶段，例如某门课程、大学期间或某个项目，以及需要保留的资料类型。优先使用用户已从 Mail 导出的目录或明确选定的附件清单；用户已指定清单或整个导出目录时，直接以该范围为准，无需补问年份。

当前 Agent 没有邮箱账号接入、按邮件日期／发件人检索、附件导出或邮件删除工具。只有“整理大学期间的邮件”而没有本地范围时，先请用户在 Mail 中筛选并导出附件，或提供已经可读取的独立文件夹；不能声称已遍历邮箱。

用户明确提供 Mail 内部可读附件路径时，可以在已授权范围内只读检查；写操作采用获授权的独立工作副本，保留 Mail 管理的原路径。`.mbox`、`.eml`、邮件数据库和索引不是可以直接交给压缩工具的普通附件；完整邮件备份需要用户另行从 Mail 导出和保管。

阶段归属依据用户导出时的筛选或用户提供的映射。文件修改时间可能是下载、复制或修改时间，不能据此判断邮件收发时间；不确定项单列，不自动放入或排除某个学年。

完成条件：阶段范围及其依据、独立附件路径已明确。仅要求处理附件时，说明不包含正文／往来记录即可；只有用户要求保留完整邮件时才补充邮件导出安排。缺少邮箱能力时给出准确的下一步，不假装已经取得附件。

## 检查与保留决策

用 `ls`／`find` 枚举指定范围，并调用对应 `inspect_*` 检查文件。按用户明确价值判断区分“保留归档”“暂不处理”“明确不需要”，不能仅因文件旧或位于缓存目录就判断可删。

| 资料                                   | 建议处理                                                                                  |
| -------------------------------------- | ----------------------------------------------------------------------------------------- |
| 课程 PDF、项目报告                     | 优先 `lossless`；对数字签名、加密、PDF/A 等当前不支持项保留完整源文件                     |
| 普通 DOCX／PPTX                        | 探测嵌入媒体，质量优先；在方案中明确整份旧文档备份和原路径替换                            |
| 截图、照片、会议录像                   | 按图片／视频探测结果及用户质量要求选择压缩；说明有损与元数据影响                          |
| 表格、源码、压缩包、邮件包等未接入格式 | 保留并列为当前不能直接登记归档的资料；普通目录复制可另列为文件副本，不能算作 Catalog 归档 |

是否保留某份资料缺少依据时，先给出候选和必要的问题；用户已选择的附件无需逐份重新询问。重复检测只在用户希望减少重复附件时使用，结果按共用契约处理，不将同名但不同版本的作业或合同视为重复。

标签根据已确认的阶段、课程／项目名称和文件名建议，先复用已有词库。只有用户明确来源时才建议具体学校、发件人或项目标签；“2022—2026 大学资料”是用户阶段标签，不代表每个文件已提取到邮件日期。

完成条件：每份候选都有处理方式或保留原因；附件归档与邮件正文、往来记录的保留安排分开说明。

## 执行压缩、备份与归档

方案包含工作副本或实际输入、输出目录、档位、原件变化、标签和是否有后续清理。确认已有授权覆盖后，按文件顺序执行：

1. 需要工作副本的项先 `mkdir`／`copy`，仅处理复制成功的文件，并保持不同来源的同名附件可区分。
2. 图片、视频、PDF 调用对应 `compress_*`；用户要求归档时追加 `archive: true` 和已确认标签。
3. DOCX／PPTX 调用 `compress_office`，同时核对 `status`、`replacementStatus`、`catalog.backupStatus`；替换成功后按 ID 调用 `archive_file`。
4. 分别核对备份、归档、标签和无收益状态。部分失败保留结果与记录 ID，按 ID 续做归档；不重新编码已移走的输入。

为以后找回，报告“用户导出的阶段／目录 → 实际处理路径 → catalog.id → 归档路径”。Catalog 没有邮件级来源模型，不能声称已保存发件人、主题、邮件正文或附件与原邮件的关系；重要对应信息由用户在导出时保留，本次对话也不是持久备份。

## 验看后按需清理

归档完成先交付记录和路径，让用户知道哪些资料仍未处理。用户要求打开验看时按归档 ID 调用 `open_archive`；返回打开请求成功不等于阅读器实际打开、公式排版正确或嵌入媒体可播放，必要时请用户在对应应用验看。

用户已授权清理独立导出副本时，仅对明确路径且已满足保留／归档要求的项调用 `trash`。备份失败、归档失败、未支持和仍待确认的附件保留；不把整个导出目录作为快捷清理目标。若需要永久删除，沿用明确包含目标和方式的用户授权。

Mail 内部附件清理、历史邮件删除、远端邮箱或 IMAP 同步效果，需要用户在 Mail 中自行确认和操作；当前没有对应工具，不用 `trash` 删除邮箱包、数据库或索引来模拟邮件删除。用户只要求归档时，到结果交付即结束。

明确说明：附件归档不包含正文、主题、收发件人与往来记录；工作副本归档也不减少 Mail 原始占用。压缩体积差、回收站处理与实际磁盘释放分别报告。

## 后续检索

按课程、项目、阶段标签或文件名调用 `search_archives`，对过多结果分页并逐步缩小范围。Catalog 的源修改日期／归档日期只用于对应含义的筛选，不回答“哪封邮件何时发来”。用户要求打开或定位时按记录 ID 操作。

交付时分别列出已归档、无收益、未支持、失败与未处理项，并写明哪些邮件级工作仍需用户在 Mail 中完成；不能把附件处理数量报告成已整理或删除的邮件数量。
