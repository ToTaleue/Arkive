## 已确定的表达原则

- 核心初衷是帮助个人用户节省电脑存储空间，同时让不常用的文件在需要时快速找到。
- 开场明确提到电脑涨价、存储与扩容成本高。不能将这个动机淡化成可有可无的背景，也不只从“不常用但舍不得删”切入。
- 清理与压缩是腾出空间的两条主要路线；归档承接冷数据的长期保留、后续迁移与快速检索。
- 少文字，多用实际结果、前后对比和操作截图。压缩数据明确写“文件体积减少 X%”，避免“压缩比 X%”含义不清。
- 面向普通用户解释方法。视频页不出现 ab-av1 等工具名，不堆编码参数和质量指标缩写。
- 质量表达以“尽量让肉眼难以察觉差异，同时尽可能压小”为目标。确定的效果结论应对应实际样本，不能承诺所有文件均视觉无损或都有相同收益。
- 数据、截图和演示以实际结果为准。未接入的能力标明规划状态，不用概念流程冒充已经跑通的演示。
- 检索价值主要通过标签提供记忆线索、组合筛选与系统原生复用来解释，不要求添加检索耗时基准，也不编造“秒级找回”等性能数字。

## 逐页内容草案

### 1. 核心痛点：电脑空间不够了，去哪里找空间？

**本页目的**：先让观众理解为什么需要 Arkive。

**必须表达**：

- 电脑涨价，存储、换机和扩容成本高。
- 文件不断积累，图片、视频和各种附件逐渐占满电脑。
- 用户希望从现有电脑里找回空间，减少为了容量而换设备或扩容的压力。

**呈现建议**：用磁盘空间不足的直观画面配一个核心问题，文字保持简短。“不常用却舍不得删”留作后续冷数据场景的补充。

**素材要求**：若加入具体价格、涨幅或价格走势图，补充对应时间、配置和来源，不编造数字。

### 2. 三个核心功能：清理、压缩、归档

**本页目的**：用一页交代产品的主要解决方式。

| 功能 | 对用户的价值 |
| --- | --- |
| 清理 | 清掉缓存、残留等不再需要的内容 |
| 压缩 | 减小图片、视频及文档体积，尽量保留观看和使用质量 |
| 归档 | 整理不常读取但需要保留的文件，用时快速找到 |

清理与压缩先解决空间占用；归档为冷数据管理及未来迁移到外置硬盘或云端做好准备。迁移是准备方向，不能直接写成当前已有一键迁移功能。

**呈现建议**：三个功能各一句话，不在此页展开底层工具。

### 3. 视频压缩：先试一小段，再决定怎么压

**本页目的**：视频作为压缩重点，单独解释方法，并直接给出结果。

**通俗方法**：

1. 抽取部分视频片段。
2. 先试压缩，评估压缩后的画面质量并得到评分。
3. 根据评分调整参数，尽量让画面差异难以被肉眼察觉，同时把文件压得更小。
4. 正式压缩并校验输出。

**自主处理的价值**：用户直接使用压缩工具时，需要自己猜参数、反复尝试；Arkive 将开源试压与质量评估方法接入流程，根据明确的质量目标选择合适参数。追求在质量目标范围内减小体积，让画质和空间取得较好的平衡，不宣称对所有视频都求得数学上的最优解。

**质量表述**：即使选择偏向体积的档位，也应依据评估标准选参，不随意设置激进参数。用户希望强调“压缩有标准、有依据”；具体档位是否达到肉眼难以察觉的效果，以对应素材的评估和实际观看为准。

**交互重点**：支持直接拖入文件，减少上手步骤。用截图或短动图表现“拖入、选档、开始压缩”，不暗示拖入后未经操作就自动执行。

**效果展示**：同一真实样本的压缩前后画面对比，醒目展示原始大小、压缩后大小、体积减少百分比。方法说明保持简短，不出现专用工具名。

**统一小字**：“结果来自所示测试样本，实际压缩效果随文件内容和原始压缩程度而异。”抽样评分不等于对整片视觉无损的保证。

### 4. 其他文件压缩：图片、PDF、Word 等

**本页目的**：其余格式集中在一页，方法一笔带过，以真实结果说明覆盖范围。

- 图片、PDF、Word 等各用一句话解释实际处理方法。
- 各类格式配真实样本数据：原始大小、压缩后大小、体积减少百分比。
- 图片可配前后局部对比；PDF、Word 可配打开效果，避免只报数字而看不到可用性。
- 不把所有格式讲成使用同一种评分方法，也不把文档处理统一描述成“人眼完全察觉不到”。

**待核对**：用户提到 TXT；初版还包含 PPTX。最终格式列表按实际支持能力、测试数据和版面确定，TXT 不能直接写成已支持。测试样本有收益才展示，不补造统一压缩率。

**统一小字**：沿用视频页的样本效果说明。

### 5. 清理：找回容易被忽略的空间

**本页目的**：一页说明清理对象、使用优势与实际效果，不展开工具细节。

**可用文案**：“软件删了，它留下的文件可能还在。”

**内容精简为**：

- 缓存、日志、临时文件与已卸载应用残留。
- 文件在本地扫描和处理，无需上传文件内容。
- 真实清理结果截图，以及醒目的“本次释放 X GB”。

如需举目录例子，可在小字中使用 `~/Library/Caches`、`~/Library/Logs` 等；说明按规则识别清理项，不能让观众理解成整个目录一律删除。强调集中发现平时容易忽略的内容，减少手动寻找和判断的成本。

**开源背书**：页脚注明“清理能力基于开源工具 Mole”。2026-10-18 查询 [Mole GitHub 仓库](https://github.com/tw93/Mole)，为 **70,847 Stars，约 7.1 万**。最终制作时更新星数并保留统计日期。星数说明社区关注度，实际清理收益用 Arkive 的实测结果体现。

**制作核对**：清理数据优先使用工具实际输出，标清预览估算与已完成清理的区别；当前有界面与隔离夹具验证，真实系统级清理仍需实际验收。离线描述针对本地清理流程，不扩展成整个应用或 Agent 永不联网，也不由离线推导出绝对删除安全。

**可靠性说明**：采用开源清理方案和已有规则，在本地发现并处理清理项，支持先预览。开源来源与规则可以查验；不将“开源”或 GitHub 星数写成不会误删的保证。直接清理会按 Mole 规则删除并默认清空回收站，不能宣称全部可撤销，具体删除影响须与产品提示一致。

### 6. 归档：不常用的文件，集中存好

**本页目的**：解释冷数据为什么要归档，以及原件与归档副本的关系。

**核心说明**：有些文件需要长期保留，却不常读取。把它们整理好，为以后转移到外置硬盘或云端做好准备，并在需要时快速找到。

**当前目录名称**：

| 用户目录下的文件夹 | 保存内容 | 默认组织方式 |
| --- | --- | --- |
| `~/Arkive Backup` | 压缩前的完整原件 | 按备份日期分日目录 |
| `~/Arkive Archive` | 可直接打开的压缩归档副本 | 按归档日期分日目录，例如 `2026-10-18` |

两个目录彼此并列，不是在一个额外的 Ark 文件夹下。Archive 按实际归档日期组织，不按源文件拍摄日期或修改日期分目录。

**呈现建议**：用一张简单示意图说明“原件备份”和“压缩副本归档”，详细标签能力放下一页。

**已明确的产品方向**：Backup 是压缩后完整原件的阶段性保留位置；后续按保留安排清理，用户明确要求时也允许立即清空。用户希望讲清楚，保留备份是为了处理后有回退余地，不是要求永久保存所有原件。

**空间收益说明**：清理备份后，按最终保留的归档文件及其他副本说明空间收益；可以对比“保留原件期间”与“清理备份之后”两种状态。备份尚未删除时确实占用磁盘，不能因为未来会清理就从当前占用或实测释放量中排除；归档时保留的原输出也应计入实际占用。

**制作核对**：定期清理任务尚未实现，保留期限、执行方式和授权规则未定；立即清空 Backup 的入口与记录联动也需核对。此处确认的是 PPT 中要解释的产品处理方式，不是本次获准实际删除任何备份。

### 7. 标签与检索：少翻文件夹，按标签找到

**本页目的**：标签是重点能力，单独一页。

**必须表达**：

- 采用 macOS 原生 Finder 标签，脱离 Arkive 后仍可使用这些标签。
- 提供预设标签，也支持已有标签与用户自定义标签。
- AI 根据文件元数据等明确线索推荐标签，优先复用预设和已有名称。
- 支持多个标签组合检索。例如同时选择“旅行”和“京都”，找到同时具备两个标签的文件。
- 标签承接人的记忆：即使忘了完整文件名，还可能记得人物、地点、活动、项目或年份，用这些线索缩小范围。
- 系统原生标签可被支持相应查询的其他 Agent 或工具复用；用户可以提供关键词，让其协助定位归档文件。是否能读取和查询标签取决于具体工具能力及权限，不能承诺所有 Agent 都能直接查到。

**效果表达**：本轮不要求为了 PPT 测量检索速度。用真实的标签组合与找回过程展示“更容易找到”，不写未经测试的速度倍数、响应时间或比其他方案更快。

**呈现建议**：用“推荐或选择标签、写入文件、组合标签找到文件”的连续截图。明确展示 Arkive 内检索和 Finder 原生标签各自的作用，不把应用内检索界面当作 Finder 截图。

**制作核对**：原生标签同步和应用内多标签 AND 检索已有实现；AI 推荐已有独立函数，描述性资料采集与推荐界面仍待接线。最终按实际交付版本展示，不将 AI 自动推荐当作已有完整演示。

### 8. 工具箱：进一步挖掘空间的实验性能力

**本页目的**：三项能力放一页，每项只保留用途与一句原理。

| 能力 | 页面简述 |
| --- | --- |
| APFS 无损去重 | 对内容相同的重复文件，通过克隆共享底层存储块，保留各自路径，后续修改互不影响 |
| 磁盘占用分析 | 看清每个目录占多少空间，快速定位大文件和异常目录 |
| 开发项目清理 | 找出 `dist`、`node_modules` 等可重建或重新下载的内容，旧项目可先清理再归档 |

**呈现建议**：工具箱或磁盘分析结果截图配短句。Mole Analyze、Purge 的技术来源可放小字。

**与下一页衔接**：发现某个文件夹特别大，再让 Agent 深入检查它为什么大、有哪些处理机会。

**制作核对**：

- 正确名称是 APFS。共享逻辑字节不等于实测释放空间；同一 APFS 卷、快照和现有共享状态等会影响实际收益，不承诺“白得很多空间”。
- 开发依赖恢复可能需要联网，不能将所有开发文件都说成无条件可删。
- 工具箱页面接入状态与底层 Service、Agent Tool 的状态分开核对；Purge 已有预览能力，不能将三项都写成当前工具箱页面已经完整可操作。

### 9. Agent：不知道从哪里下手？直接告诉 Arkive

**本页目的**：回应“功能很多，初次上手不知道怎么用”的问题。

**希望强调的设计**：把支持的业务功能封装成 Agent 可调用的工具。用户通过对话说明需求，Agent 检查文件、推荐方案，并在授权后调用工具执行。

**对话示例草案**：

> 用户：这个旧项目文件夹太占空间，帮我看看怎么处理。
>
> Agent：我先分析空间占用，看看有哪些可重建的开发文件、适合压缩的素材，再给你整理和归档方案。

方案得到用户明确授权后执行，不把这段示例当作已经发生的真实模型结果。核心价值是把前面分散的能力串成一次容易理解的操作。

**工具边界与操作保护**：Agent 使用团队选定、接入的工具，通过业务接口执行，未开放任意 shell。具体格式检查、质量评估、输出校验及系统关键路径保护由对应工具和业务代码落实。对话中的授权判断与程序硬保护分开说明，不把当前实现描述成所有操作均有独立代码审批、严格目录沙箱或绝对不会误操作。

**场景 Skill 与工具特化**：用户确认的方向是把具体场景整理成 Skill，供 Agent 按场景调用，并在工具层实现设备、格式与业务所需的特化。Skill 说明场景流程与使用方法，实际处理及校验仍由业务工具承担；以此解释如何从一句需求进入多步操作。当前产品尚未加载 `SKILL.md`，微信 Skill 是文档草案，制作时按接入进展区分设计与完成状态。

**制作核对**：用户希望强调“所有支持功能都接入 Agent”，最终需核对工具覆盖范围。当前独立页面的真实 Mole Clean 没有对应的 Agent 直接执行工具，原有 Clean 预览与授权后的文件处理链路仍在；不能仅凭功能页存在就写成全部已接入。Agent 对话可能联网，本地文件处理与模型请求要分开描述。

### 10. 自主贡献：把节省空间变成普通人能完成的流程

**本页目的**：回应“这些工具都已有，Arkive 自己做了什么”，对应方案创新与差异化价值。

**核心陈述**：围绕“节省空间”这一共同目标，将已有工具与系统能力组织成普通用户可以完成的处理流程，提供简单的窗口和方便的 Agent 对话交互。

**页面只保留三个重点**：

- **目标与流程**：围绕空间问题，串联分析、清理、压缩、备份、归档与检索，让用户知道下一步做什么。
- **简单窗口**：拖入文件、选择档位、查看结果、归档与找回，减少手动使用多种工具的成本。
- **Agent 交互**：通过对话了解需求、探索问题、推荐方案，并调用已接入工具完成授权操作；具体场景通过 Skill 组织是已确认方向。

**讲述补充**：视频试压评分与选参、大疆素材处理、原件和归档副本的管理，是这些流程如何落地的具体例子，前面的功能页已展示，不在这里重复讲参数。

**开源关系**：底层编解码、质量评估方法、清理方案、Agent 框架和文件系统能力来自相应开源项目或系统；自主贡献放在产品与流程设计、业务接线、特化、校验和交互。不能把集成已有方法写成自研压缩算法、原创质量指标或自创 APFS 克隆机制。第三方详细来源保留在技术材料和附录。

### 11. 应用场景一：演唱会录下来了，电脑却快装不下了

**场景**：用大疆 Pocket 拍摄的演唱会录像很大，希望保留回忆，又不想让素材一直占满电脑。

**流程**：

1. 把录像拖入 Arkive，选择质量档位。
2. 自动采样、试压评分，完成压缩与输出校验。
3. 保存完整原件备份，给压缩结果添加“演唱会、歌手、日期”等标签并确认归档。
4. 以后按名称或标签找到归档视频。

**大疆 Pocket 针对性适配**：

- 默认 HEVC 路径在已验证的 Pocket 3 样本上保留 4K、帧率、10bit 及色彩标记。
- 兼容的音轨直接保留，不重复压缩；已有样本的 AAC 音频包一致性校验通过。
- 识别设备附加数据、时间码和封面，处理前告知移除内容，完整原件另行保留。

**可用数据旁证**：已有 Pocket 3 短片测试从 **419,355,104 字节降至 109,906,904 字节**，可显示约 **419.4 MB → 109.9 MB，文件体积减少 73.8%**，这里 MB 采用十进制。该数值来自历史 HEVC 自动选参整段测试，不能与后续参数调整的耗时拼成同一次结果，也不能标成演唱会录像的实测值。

正式展示优先替换为实际演唱会素材的对比画面与数据。小字标注样本来源和效果差异，不承诺覆盖大疆全部录制模式；旧规划提及 `.LRF` 代理文件清理，尚未确认接入，不能作为已支持能力。

### 12. 应用场景二：微信文件归档，用时按名称找回

**场景**：微信收到的文件越积越多，很多平时用不上，偶尔需要时又难翻到。

**流程**：

1. 选择需要整理的微信文件或附件。
2. 适合压缩的先压缩，再归档保存。
3. 以后记得文件名或部分关键词，就能在归档记录中搜索并打开。

确认不需要的文件，用户也可以选择直接删除；删除与保留归档是按需选择的处理方式，不描述成一律自动清空。

**呈现建议**：选择微信文件、归档、输入文件名找到结果的连续截图，重点是“不用再翻聊天记录”。

**制作核对**：范围是用户指定的可读取文件，不承诺读取全部聊天、解密数据库或加密图片。微信专用场景编排仍需核对交付状态，不能把早期“一次性清空微信”的规划当成当前已实现流程。

### 13. 应用场景三：毕业了，整理过去的邮件附件

**场景**：Mac 本地邮件积累了几年的课程资料、项目文件和附件。毕业或一个阶段结束后，集中整理一次。

**流程**：

1. 按大学期间、某个项目期间等阶段选择本地邮件附件。
2. 对值得保留的附件压缩、添加标签并归档。
3. 确认归档文件可打开、可检索后，再按需清理本地附件。
4. 用户也可决定是否清空不再需要的历史邮件。

**重点表达**：“先把值得保留的资料归档好，再整理旧邮件。”保留和校验让后续清理更有把握，压缩本身不能替代备份。

**制作核对**：附件归档不包含邮件正文和往来记录；若删除历史邮件，需要单独决定这些信息是否保留。Mac 本地邮件的接入方式尚未确认，当前作为应用场景方向，不冒充已完成的邮箱演示。

### 14. 更多应用场景：还有这些空间，也值得整理

**本页目的**：以下场景合在一页，每项一句话，不再分别展开。

- **摄影照片**：批量压缩 Lightroom 等导出的照片，保留可承载的拍摄信息。
- **会议录像**：压缩历史录制，按时间归档。
- **工作资料**：整理 PDF、截图和设计稿，用时快速检索。
- **旧项目与冷文件**：清理可重建产物，归档长期不用的资料。
- **软件缓存与旧下载**：找出容易忽略的空间占用。
- **网盘本地副本**：整理同步文件的本地占用。

**呈现建议**：图标配短句，保持一页；专用场景仍属规划的部分需准确标明，不能暗示已经支持所有软件或网盘的自动处理。

### 16. 总结：少占空间，随时可寻

**核心理念**：

> 少占空间，随时可寻。

**补充一行**：

> 帮你腾出电脑空间，也让不常用的文件，在需要时快速找到。
